# План гиперлокализации Stone AI

Дата: 2026-05-27  
Проект: Stone AI, `stoneai.ru`  
Цель: создать масштабируемую систему городских SEO-страниц, которая дает органический трафик и заявки без риска doorway/spam-страниц.

---

## 1. Краткая стратегия

Гиперлокализация для Stone AI имеет смысл, но ее нельзя делать как массовую замену `[город]` в одном шаблоне. Правильная модель: каждая городская страница должна отвечать на реальный локальный спрос и показывать, как Stone AI полезен бизнесу именно в этом городе.

Основная ставка:

- городские посадочные страницы под коммерческий спрос;
- связки `город + ниша + AI-услуга`;
- внутренняя перелинковка с текущими SEO-разделами сайта;
- быстрая проверка спроса на первой партии городов;
- масштабирование только после данных из GSC, Яндекс.Вебмастера и Метрики.

Не делаем:

- 100-1000 одинаковых страниц с заменой города;
- скрытые страницы без нормальной навигации;
- автогенерацию без редакционного контроля;
- keyword stuffing списками городов;
- IP-зависимые версии, которые бот не может стабильно проиндексировать.

---

## 2. Почему нужен осторожный подход

Google прямо относит к doorway abuse страницы, созданные под похожие запросы, если они ведут пользователя к одному и тому же финальному месту и не дают самостоятельной пользы. В их примерах есть страницы под регионы/города, которые просто funnel users to one page.

Источник: https://developers.google.com/search/docs/essentials/spam-policies

Google также считает, что похожие региональные варианты могут стать дублями, а canonical является сигналом, не жестким приказом. Если страницы слишком похожи, поисковик может выбрать не ту страницу как основную.

Источник: https://developers.google.com/search/docs/crawling-indexing/canonicalization

Яндекс отдельно предупреждает, что дубли тратят crawl budget, конкурируют между собой и могут привести к исключению важной посадочной из поиска. Для региональных версий Яндекс рекомендует добавлять реально релевантную региону информацию и делать все страницы доступными роботу независимо от IP.

Источники:

- https://yandex.com/support/webmaster/en/yandex-indexing/about-doubles
- https://yandex.com/support/webmaster/en/site-geography/site-region

Вывод: городские страницы допустимы, если каждая страница является полноценной посадочной с уникальной ценностью, а не промежуточной SEO-прокладкой.

## 3. Бизнес-цели

### Основная цель

Получить дополнительный органический трафик по низко- и среднечастотным коммерческим запросам:

- `нейросеть для бизнеса Казань`;
- `чат бот для бизнеса Казань`;
- `ai ассистент для ресторана Сочи`;
- `автоматизация заявок салон красоты Краснодар`;
- `нейросеть без vpn Москва`;
- `ai для маркетинга Екатеринбург`.

### Вторичные цели

- Увеличить количество целевых входов не только на блог, но и на коммерческие страницы.
- Создать сеть страниц, которые усиливают разделы `/chatbot`, `/tools`, `/use-cases`, `/for`, `/models`, `/pricing`.
- Получить больше запросов в Яндекс/Google по региональной семантике.
- Собрать данные: какие города, ниши и формулировки реально дают показы/клики.
- Подготовить основу для страниц `город + ниша` после проверки первой версии.

### KPI первой версии

Период оценки: 45-90 дней после индексации.

Минимальные KPI:

- 10-15 городских страниц в индексе Google и Яндекса;
- первые показы по 30-100 региональным запросам;
- CTR выше 1.5% по страницам с позициями 5-20;
- 3-10 органических лидов или регистраций с раздела `/locations`;
- отсутствие массовых дублей в GSC и Яндекс.Вебмастере.

Нормальные KPI:

- 300-1000 показов в месяц по первой партии;
- 30-80 кликов в месяц через 2-3 месяца;
- 1-3 страницы с явной traction, которые можно развивать в `город + ниша`;
- 1-2% конверсия в регистрацию/чат/переход к тарифам.

## 4. Рекомендуемая URL-структура

### Базовый слой

```txt
/locations
/locations/moscow
/locations/spb
/locations/kazan
/locations/sochi
/locations/krasnodar
```

Плюсы:

- понятно для пользователя;
- легко добавить в sitemap;
- легко связать с текущими разделами сайта;
- не создает отдельных поддоменов и проблем с региональной модерацией;
- проще контролировать canonical и дубли.

### Второй слой после проверки спроса

```txt
/locations/kazan/ai-chatbot-for-restaurants
/locations/sochi/ai-assistant-for-hotels
/locations/moscow/ai-sales-automation
/locations/spb/ai-for-clinics
```

Второй слой запускать только после данных по базовым страницам. Не делать сразу.

### Чего избегать

```txt
/moskva
/spb
/kazan
```

Проблема: нет понятной иерархии.

```txt
moscow.stoneai.ru
spb.stoneai.ru
```

Проблема: для текущего масштаба это лишняя сложность. У Яндекса есть отдельные рекомендации по региональным поддоменам, и одинаковый контент может быть признан alternate address.

```txt
/locations/moscow
/regions/moscow
/city/moscow
```

Проблема: распыление дублей.

Каждая базовая городская страница должна таргетировать один главный интент:

```txt

```

Не нужно пытаться впихнуть в одну страницу все запросы. Ниши и конкретные функции идут в блоки и будущие дочерние страницы.

## 7. Контент-модель городской страницы

### Минимальный объем

Для первой версии:

- 900-1400 слов на страницу;
- 35-55% текста должно быть уникальным для города;
- уникальный title;
- уникальный description;
- уникальный H1;
- уникальный блок ниш;
- уникальные примеры сценариев;
- уникальный FAQ минимум 4 вопроса;
- уникальный CTA-акцент.

### Структура страницы

#### 1. Hero

H1:

```txt
AI-ассистент для бизнеса в [город]
```

Подзаголовок:

```txt
Stone AI помогает компаниям в [город] быстрее отвечать клиентам, обрабатывать заявки, готовить контент и автоматизировать рутинные задачи через 65+ нейросетей в одном интерфейсе.
```

CTA:

- `Попробовать Stone AI`;
- `Открыть AI-чат`;
- `Посмотреть тарифы`.

Hero должен быть коммерческим, без абстрактного SEO-текста.

#### 2. Кому полезно в городе

Блок зависит от города.

Пример для Сочи:

- отели и апартаменты;
- рестораны и кафе;
- экскурсионные бюро;
- аренда транспорта;
- салоны и локальные услуги.

Пример для Екатеринбурга:

- B2B-продажи;
- производственные компании;
- HR и рекрутинг;
- образовательные проекты;
- сервисные компании.

#### 3. Основные сценарии

Каждая страница должна иметь 5-7 сценариев. Часть общая, часть локальная.

Общие сценарии:

- ответы клиентам в чате;
- подготовка текстов для сайта, Telegram, VK, email;
- генерация изображений и видео для рекламы;
- анализ документов;
- помощь менеджерам по продажам;
- быстрые ответы на типовые вопросы;
- перевод и адаптация текстов.

Локальные сценарии:

- для Сочи: сезонные акции, ответы туристам, бронирования;
- для Москвы: обработка большого потока заявок, сравнение предложений, скрипты продаж;
- для Казани: локальные акции, меню, отзывы, заявки в WhatsApp/Telegram;
- для Екатеринбурга: B2B-письма, КП, технические описания.

Таблица:

|---|---|---|

- 3-6 ссылок на продуктовые разделы;
- 2-4 ссылки на блог/answers/use-cases;
- breadcrumbs.

#### 9. Финальный CTA

Финальный CTA должен быть не "оставьте заявку", а конкретный:

```txt
Запустите AI-помощника для задач вашего бизнеса в [город]: клиентские ответы, контент, документы, изображения и видео в одном кабинете.
```

## 10. Техническая реализация в текущем проекте

Текущий сайт использует Next.js App Router. Поэтому реализацию лучше делать в стиле уже существующих динамических SEO-разделов: данные в `website/lib`, страницы в `website/app`, sitemap в `website/app/sitemap.ts`.

### Новые файлы

```txt
website/lib/locations.ts
website/app/locations/page.tsx
website/app/locations/[slug]/page.tsx
```

Опционально:

```txt
website/components/locations/LocationHero.tsx
website/components/locations/LocationUseCases.tsx
website/components/locations/LocationFAQ.tsx
website/components/locations/LocationGrid.tsx
```

Если страница получается простой, можно начать без отдельной папки компонентов.

### Data model

Пример структуры в `website/lib/locations.ts`:

```ts
export type LocationPage = {
  slug: string;
  city: string;
  prepositional: string;
  region?: string;
  title: string;
  description: string;
  h1: string;
  lead: string;
  primaryIndustries: string[];
  useCases: {
    title: string;
    text: string;
  }[];
  localExamples: {
    title: string;
    text: string;
  }[];
  faq: {
    question: string;
    answer: string;
  }[];
  relatedCities: string[];
  relatedLinks: {
    label: string;
    href: string;
  }[];
  updatedAt: string;
};
```

### `generateStaticParams`

Городские страницы должны быть статически сгенерированы:

```ts
export function generateStaticParams() {
  return LOCATIONS.map((location) => ({ slug: location.slug }));
}
```

### `generateMetadata`

Для каждой страницы:

- уникальный `title`;
- уникальный `description`;
- canonical `/locations/[slug]`;
- OpenGraph с теми же title/description;
- robots index/follow.

### `notFound`

Если slug не найден:

```ts
notFound();
```

### Sitemap

Добавить в `website/app/sitemap.ts`:

```ts
import { LOCATIONS } from "@/lib/locations";
```

И блок:

```ts
const locationPages: MetadataRoute.Sitemap = [
  {
    url: `${SITE_URL}/locations`,
    lastModified: now,
    changeFrequency: "weekly",
    priority: 0.75,
  },
  ...LOCATIONS.map((location) => ({
    url: `${SITE_URL}/locations/${location.slug}`,
    lastModified: new Date(location.updatedAt),
    changeFrequency: "monthly" as const,
    priority: 0.72,
  })),
];
```

Добавить `...locationPages` в return.

### Robots

Ничего отдельно закрывать не нужно. Страницы должны быть доступны к индексации.

### Canonical

Каждая городская страница должна иметь self-canonical:

```ts
alternates: {
  canonical: `/locations/${location.slug}`,
}
```

Не ставить canonical всех городов на `/locations` или главную. Тогда страницы почти гарантированно не будут конкурировать как самостоятельные посадочные.

### Structured data

На каждой странице:

1. `BreadcrumbList`;
2. `Service`;
3. `FAQPage`.

Пример `Service`:

```json
{
  "@context": "https://schema.org",
  "@type": "Service",
  "name": "AI-ассистент для бизнеса в Казани",
  "provider": {
    "@type": "Organization",
    "name": "Stone AI",
    "url": "https://stoneai.ru"
  },
  "areaServed": {
    "@type": "City",
    "name": "Казань"
  },
  "serviceType": "AI tools, chatbot, business automation"
}
```

Для `FAQPage` использовать только вопросы, которые видны на странице.

### Внутренняя навигация

Добавить ссылку на `/locations`:

- в футер;
- из `/for`;
- из `/use-cases`;
- из `/chatbot`;
- из 2-3 релевантных блог-статей.

Не нужно добавлять список всех городов в глобальный футер, если он раздувает интерфейс. Лучше одна ссылка `Города`, а на `/locations` уже полный список.

## 17. Критерии масштабирования

### Можно расширять город

Если страница за 30-60 дней:

- получила показы;
- имеет CTR выше 1%;
- не признана дублем;
- имеет хотя бы несколько запросов с городом/нишей;
- дает поведенческие сигналы не хуже среднего по сайту.

Действие:

- усилить страницу;
- добавить 1-2 дочерние страницы `город + ниша`;
- добавить больше внутренних ссылок.

### Нужно улучшать

Если:

- показы есть, кликов нет;
- позиция 10-30;
- CTR ниже 1%;
- запросы релевантные.

Действие:

- переписать title/description;
- усилить первый экран;
- добавить более конкретные примеры;
- добавить блок под запросы, которые уже появились в GSC.

### Нужно остановить

Если:

- нет показов 60-90 дней;
- страница помечена как duplicate;
- нет уникального локального смысла;
- нет возможности добавить нормальный контент.

Действие:

- объединить;
- переписать;
- временно noindex, если это слабая автогенерация;
- не масштабировать подобные страницы.

## 18. Риски и защита

### Риск: doorway pages

Причина:

- страницы почти одинаковые;
- все ведут к одному CTA;
- нет самостоятельной пользы.

Защита:

- уникальные локальные блоки;
- разные ниши;
- разные примеры;
- нормальная навигация;
- раздел `/locations` как browseable hierarchy;
- не создавать сотни страниц сразу.

### Риск: дубли

Причина:

- одинаковый текст;
- одинаковые title/description;
- одинаковые FAQ.

Защита:

- self-canonical;
- уникальные метаданные;
- минимум 35-55% уникального текста;
- ручной редакционный аудит;
- мониторинг GSC и Яндекс.Вебмастера.

### Риск: crawl budget

Причина:

- слишком много страниц сразу;
- слабые страницы не индексируются;
- поисковики тратят обход на низкую ценность.

Защита:

- Phase 1 только 12 городов;
- Phase 2 только после данных;
- регулярная чистка слабых страниц;
- sitemap только для качественных страниц.

### Риск: конверсия ниже ожиданий

Причина:

- локальный пользователь не понимает, зачем ему Stone AI;
- страница слишком SEO-шная;
- CTA ведет не туда.

Защита:

- первые экраны делать коммерческими;
- CTA на реальные инструменты;
- конкретные сценарии;
- тестировать разные CTA по городам.

### Риск: неверное позиционирование

Stone AI сейчас выглядит как AI-агрегатор для широкого использования. Городские страницы могут создать ожидание полноценного B2B-внедрения "под ключ".

Защита:

- не обещать индивидуальное внедрение, если его нет;
- формулировать как "инструменты для бизнеса", "AI-ассистент", "65+ нейросетей";
- если есть чатбот/интеграции, выделять их отдельно и честно.

2. Добавить 12 городов с data model.
3. Создать `website/app/locations/page.tsx`.
4. Создать `website/app/locations/[slug]/page.tsx`.
5. Добавить metadata и canonical.
6. Добавить JSON-LD.
7. Добавить страницы в `website/app/sitemap.ts`.
8. Добавить ссылку на `/locations` в футер.
9. Запустить `npm run build`.
10. Проверить локально 3 страницы.
11. Задеплоить.
12. Проверить production.
13. Отправить sitemap/IndexNow.
14. Через 7/21/45 дней обновить документ результатами.

## 24. Итоговая рекомендация

Гиперлокализацию стоит делать, но как контролируемую SEO-продуктовую систему, а не как массовую генерацию городов. Оптимальный путь для Stone AI:

1. Запустить 12 качественных городских страниц.
2. Измерить индексацию и первые запросы.
3. Усилить страницы, где есть показы.
4. Только потом расширять города и создавать страницы `город + ниша`.

Такой подход медленнее, чем генерация сотен URL, но намного устойчивее: меньше риск дублей и doorway-сигналов, выше шанс получить коммерческий трафик, и проще превратить страницы в реальные точки входа в продукт.
